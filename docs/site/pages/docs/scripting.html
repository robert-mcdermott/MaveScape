AI agents

mavescape mcp is a Model Context Protocol server: an AI agent such as Claude Code calls MaveScape's actions as its tools, under the same names and with the same arguments as a script. It starts MaveScape with remote control on, speaks MCP on its stdin and stdout, and opens the window when a tool first needs it; when the agent closes stdin, MaveScape stops. For Claude Code:

$ claude mcp add mavescape -- ~/.local/bin/mavescape mcp

Claude Desktop, Cursor, VS Code, OpenAI's Codex and any other client that starts a server on stdio take the program's full path with the argument mcp; docs/MCP.md gives each one's configuration, the options, a check that MaveScape answers, and what to do when it does not. Then ask, as you would ask a colleague at the bench:

  • "Open the GRB2 SH3 example. What does its quality control say, and does the variance beyond counting change how far I can trust the scores?"
  • "Score it again with the DiMSum-compatible preset and compare the two runs. Which variants change class, and why?"
  • "Which positions tolerate no substitution? Show them on PDB 2VWF, and make a figure of the map and the structure."

The agent starts with get_state and works through the same steps you would, in the window you watch. Scores are research evidence of a variant's functional effect in its assay; MaveScape's instructions to the agent say never to call a variant pathogenic or benign.

Reviewing an agent's changes

An agent's changes are proposals. What it makes (a run, a selection, a figure or a panel of yours, a track, a saved view, an analysis kept in the report, a checkpoint, a table it opens into your workspace) is made at once and marked proposed, so that it and you can use it meanwhile. A design it sets or drafts, QC thresholds and acknowledgements, a target's check, the MaveDB details and every removal wait until you accept them: the Experiment view shows a proposed design beside yours with how they differ, the QC view what is proposed of QC, and the views strike out what would be removed. Opening a workspace, what the window shows, and exports are not proposals.

Claude Code worked on the GRB2 example: it scored the counts again with the DiMSum-compatible preset and saved the least tolerant core (made, marked proposed), and proposed acknowledging the bottleneck (waiting).

The strip above the view says who proposes how many changes; Review lists them, made and waiting. Accept all applies what waits, under the agent's name, and keeps what was made; Reject all removes what was made, with what you built on it since (MaveScape asks first), and drops what waits. Each decision is one entry of the history, yours, and can be undone. The agent asks proposals what is open and what you decided; score waits for a design it proposed, and nothing is certified while a proposal is open.

Accepted: the acknowledgement applies, under Claude Code's name, after your decision; every change the agent made carries its name.

Every change goes into the workspace's history with the agent's name (the name its client gives), which the history's chain covers. The report's decision log names the agent beside its changes, its AI agents section says what agents proposed and you accepted, and a checkpoint's diff names who proposed what was added.

What an agent reads and sees

Each result is the action's sentence and its data. scores gives a run's variants as a table with the columns of its scores export (filtered by position, kind, a selection or a query, sorted, 100 rows at a time), and provenance a run's provenance. The agent looks at pictures: the map (render_map with image, the whole target or a stretch of positions), the Structure view (render_structure) and the figures' pages (figures with image), which a script gets as data URLs. Each tool carries MCP's hints: whether it only reads, whether it replaces or removes something, and whether it may ask a public service. Files are read and written by absolute path, an existing file never replaced unless the call says so. An action MaveScape refuses comes back with its reason, which the agent can act on.

Everything runs on this computer: MaveScape answers only requests from it, and your tables never leave it. The agent acts through the window you use, nothing out of sight.

A session on Hsp90

What working with an agent looks like, on the Hsp90 example: nine positions of yeast Hsp90, every codon, grown for 21 generations in one replicate (Hietpas et al. 2011). Each tool call below is real: validation/agent-session.mjs makes them through mavescape mcp in CI and checks every number the answers quote. The answers were written by Claude from those results; another agent's wording will differ, its numbers not.

YouOpen the Hsp90 example. How well do its scores agree with the published fitness, and what does quality control say about them?

  • open_example {"id": "hsp90"}
  • qc_findings {"run": "Run 1"}
  • compare {"a": "Run 1", "b": "urn:mavedb:00000011-a-1", "scale": "stated", "direction": "higher-more"}
  • scores {"run": "Run 1", "kinds": ["nonsense"], "limit": 0}
The agent

Run 1, scored with MaveScape's defaults per generation, ranks the 187 variants it shares with the record's published scores much as they do (r 0.95). Stated to be on one scale, though, they agree poorly: Lin's concordance is 0.48, Run 1 is higher by 0.22 on average, and the difference grows with the effect (a Bland–Altman slope of −0.91), most at W585, S586 and A587 (0.34 to 0.39).

Quality control fails the fit of the time courses: they scatter about 44 times more than counting predicts. With one replicate, the agreement between replicates and the variance beyond counting are not assessed. The stops fall to the floor within a few generations, so a line through all eight samples flattens them (a median of −0.32 per generation). The authors fitted their null-like variants on the first three samples only. I can fit those three, keeping the present analysis in a checkpoint to compare with.

YouDo that.

  • checkpoint {"name": "All eight samples"}
  • provenance {"run": "Run 1"}, for the design it was scored with
  • set_design with that design, generations 9 to 21 not used (ignoredColumns, the reason "later time points: the authors fit their null-like variants on the first three")
The agent

I kept the checkpoint "All eight samples" and proposed a design that fits generations 0, 3 and 6: the columns Gen_9 to Gen_21 not used, with the reason. The design waits for you; Experiment shows it beside yours. Accept it, and I'll score with it.

The proposal reviewed: the published scores' annotation and the checkpoint made, the design waiting, shown beside yours with what it changes.

Had the agent scored now, MaveScape would have refused: a run scored meanwhile would have your design, not the one it means. You accept in the strip, then ask on.

YouAccepted. Score it and tell me what changed.

  • score {"parameters": {"timeScale": "unit"}}, per generation as Run 1
  • diff {"from": "All eight samples"}
  • scores {"run": "Run 2", "kinds": ["nonsense"], "limit": 0}
  • inspect_variant {"variant": "p.Trp4Ter", "run": "Run 2"}
  • compare {"a": "Run 2", "b": "urn:mavedb:00000011-a-1", "scale": "stated"}
The agent

Run 2 fits the first three samples, per generation like Run 1. Since the checkpoint, 148 of the 188 variants moved beyond their earlier 95% interval and 102 changed class, 93 of them from lower than the wild type to like it: over six generations, most substitutions have barely begun to fall. The stops fall faster at first, a median of −0.41 per generation against −0.32, but still not as fast as published: p.Trp4Ter scores −0.51 here and −0.73 to −0.79 in the record, one score per codon.

Against the published scores Run 2 agrees less, not more (r 0.82, Lin's concordance 0.44): the authors fitted only their null-like variants on three samples and the rest on all eight, which one design for every variant cannot do. Run 2 is a sensitivity analysis, then, not a replacement: the choice of time points moves most of the scores. It is proposed; keep it, or reject it and it goes.

Run 2 waits in the strip, made and marked proposed: Accept all keeps it, Reject all removes it with what you built on it since. The checkpoint, the design and your decisions stay in the history, each change of the agent's under its name, and Report's diff from the checkpoint shows what moved, on a map of the change.

From R and Python

The R and Python packages make each action a function, with its arguments and help: they find the running MaveScape through remote.json, give tables as data frames and pictures as files, and raise an error carrying MaveScape's reason when an action is refused. They are installed from the repository, and their version is MaveScape's.

$ pip install "git+https://github.com/robert-mcdermott/MaveScape#subdirectory=clients/python"
import mavescape

ms = mavescape.connect()                      # finds the running MaveScape
ms.open_files(["/data/counts.csv", "/data/target.fasta"], new_workspace=True)
ms.draft_design()
run = ms.score()["name"]
findings = ms.qc_findings().frame()           # a data frame (pandas)
scores = ms.scores(run=run, limit=0).frame()  # every variant, the columns of scores.csv
ms.render_map(run=run, file="/data/map.png")
ms.export("scores", "/data/scores.csv", run=run)
> remotes::install_github("robert-mcdermott/MaveScape", subdir = "clients/r")
library(mavescape)
ms_connect()
ms_open_example("grb2-sh3")
scores <- as.data.frame(ms_scores(run = "Run 1", limit = 0))
lowest <- as.data.frame(ms_scores(run = "Run 1", kinds = "missense", sort = "score", limit = 10))
ms_render_map(run = "Run 1", file = "grb2-map.png")

Two examples go further, and CI runs both against a build of MaveScape: a Python notebook on GRB2 (clients/examples/grb2-sh3.ipynb: the example opened, checked and its QC read into data frames, scored again with the DiMSum-compatible preset, both runs against the record's published scores, and a figure exported as PDF and PNG) and an R script on DHFR's two conditions (clients/examples/dhfr-lon.R: each condition's fast growers, the authors' unweighted regression against the published scores, the differences +Lon − −Lon called, which residues they replace, and where, as a plot and as MaveScape's map).

help(ms.scores) and ?ms_scores describe each action; clients/README.md says how the connection is found, and how tables, pictures and errors come back. A script's client name ("Python", "R", or yours) appears in the window's log beside each action. Without a package, the HTTP API needs nothing but JSON: the standard library's urllib.request posts {"action": …, "args": …} to /api/remote/action with the token from remote.json (on macOS in ~/Library/Application Support/MaveScape, on Linux ~/.config/MaveScape, on Windows %AppData%\MaveScape, unless MaveScape was started with --data-dir).

Remote control

The actions the agent and the clients use are MaveScape's remote control, open to any program on your computer that speaks JSON.

$ mavescape --remote-control

MaveScape prints the address actions go to and the token that reading and writing files need, and writes both to remote.json in its data folder, readable only by you (~/Library/Application Support/MaveScape/remote.json on macOS), so scripts can find a running MaveScape without being told. The file is removed when MaveScape stops.

{
  "url": "http://127.0.0.1:8820",
  "token": "…",
  "version": "{{version}}",
  "pid": 41237
}

Only programs on this computer can use remote control, addressing it as 127.0.0.1 or localhost, and web pages on other sites cannot. A MaveScape started with --remote-control while another is running starts on the next free port rather than handing its files over, so the script reaches a window it can drive.

Sending an action

POST {"action": …, "args": {…}} to /api/remote/action. The answer is {"ok", "message", "data"}: the message in words, the data for scripts.

$ curl -s http://127.0.0.1:8820/api/remote/action -d '{"action": "open_example", "args": {"id": "grb2-sh3"}}'
$ curl -s http://127.0.0.1:8820/api/remote/action -d '{"action": "qc_findings"}'

Names are forgiving: "grb2" finds the GRB2 example, "Run 2" or "2" a run, W36A the variant p.Trp36Ala. A wrong name is answered with the choices. Actions run one at a time, in the most recently opened window; GET /api/remote/tools lists every action with its arguments as JSON Schema.

Reading and writing files

open_files and export need the header X-MaveScape-Token with the token from remote.json: another user of a shared computer can reach the loopback port, but not your files. Exports take an absolute path whose folder exists, and never replace a file unless the call says "overwrite": true. The file is written through a temporary file renamed into place, so a reader never sees half of it.

$ TOKEN=$(python3 -c 'import json, os; print(json.load(open(os.path.expanduser("~/Library/Application Support/MaveScape/remote.json")))["token"])')
$ curl -s http://127.0.0.1:8820/api/remote/action -H "X-MaveScape-Token: $TOKEN" -d '{"action": "export", "args": {"what": "scores", "path": "/tmp/grb2_scores.csv"}}'

Headless runs

mavescape run scores a count table with its design without a window, for pipelines and continuous integration. It starts MaveScape on a private port with a temporary library, opens it in a headless Chrome (or Chromium, Edge or Brave: --chrome, or the CHROME variable), performs the analysis through the actions above, writes the files to a folder and stops.

$ mavescape run --design design.json --out results/ counts.csv

It checks first: the table's variant names against the design's target, the design against the table's columns, and the parameters against the design. When anything blocks scoring it scores nothing. Then it scores, with MaveScape's defaults or --preset enrich2, dimsum or vampseq, and --parameters params.json for the parameters to change (as the score action takes them). It runs the quality control and writes the run's files. A table of barcodes is named with its barcode-to-variant map (counts.csv map.csv); a target not in the design is given with --target.

The same bytes again. The scores, counts, QC, map, methods and references are the same bytes for the same inputs. The provenance and the workspace archive also record when they were made: give --time 2026-10-09T12:00:00Z, or set SOURCE_DATE_EPOCH, and every record carries that time, so every file is the same bytes. --from-workspace analysis.msz (with --run "Run 2", else the latest) reruns a saved run. Its scores are recomputed from its recorded table, design and parameters and must have its recorded output hash; otherwise the run stops.

Exit status: 0 when done. 1 when the run was not done or found a blocking problem: a design that does not fit the table, parameters that cannot score, a run that did not reproduce, a QC finding that blocks (a sample with no counts), or with --strict any failing finding not acknowledged (the files are still written). 2 for a wrong command line, a missing input, an output folder that is not empty (unless --overwrite), or no browser. run.json says why. --log json prints the progress as one JSON object per line, for a pipeline's logs.

Findings expected here. --acknowledge id=reason (repeatable) acknowledges a QC finding before the QC is read, as the QC view's Acknowledge… does (Quality control). The finding keeps its status and --strict reports it, but does not fail on it. The reason is in run.json, qc_findings.csv and the methods. A finding that passes needs no acknowledgement and is left alone, so a pipeline can name what it expects on every data set.

$ mavescape run --design design.json --out results/ --strict --acknowledge "coverage=an error-prone PCR library" counts.csv

mavescape validate checks tables, a design and parameters as scoring would, without scoring, and lists what blocks scoring and the warnings. It then says what each analysis can do with these files: the analyses that are partial or not possible and why, and what is missing, why it matters and where it is usually found (What the analysis can do). It exits 0 when they are valid and 1 when not; --json prints the report as JSON, the readiness as data in readiness. A design alone is checked without its table, and a score table against its target (--target).

Exporting a saved run

$ mavescape export --format mavedb --out deposit/ --details details.json analysis.msz

mavescape export writes a run of a saved workspace (the latest, or --run) without a window. --format mavedb writes it as a MaveDB deposit: the scores, counts, column descriptions, experiment and score set as MaveDB takes them (Depositing in MaveDB), one folder per condition when there are several (or --condition). --details details.json sets the MaveDB details first, as the set_mavedb_details action takes them:

{"abstract": "…", "license": "CC0", "publications": ["PubMed 29785012"], "contributors": ["0000-0002-1825-0097"]}

What MaveDB requires that the workspace lacks is said on standard error and in export.json, and named in the deposit's README; the files are written all the same, and --strict exits 1 instead. --format tables writes the run's tables, methods and record as mavescape run does, from the saved workspace. --format figures writes every figure of the workspace as SVG, PDF and PNG at 300 dpi, each with its manifest, and figures.json listing the manifests (Figures). --format report writes the workspace's report, report.md and report.bib (Report), and --format review its review report, review.html (The review report). With --time (or SOURCE_DATE_EPOCH) every file is the same bytes for the same workspace. Nothing is sent to MaveDB: upload the deposit yourself.

Verifying a certificate

$ mavescape verify --data tables/ analysis.certificate.msz

mavescape verify verifies a reproducibility certificate without a window, in a headless page as mavescape run uses. It checks the certificate's fingerprint, its files and its history, then computes every number again from its files and compares them bit for bit (Certificates). --data names a folder, or a file, with the tables a certificate made without them names; they are found by their SHA-256. --report verification.json writes what was found as JSON, and --review review.html the review report of the certificate verified (The review report). Exit status: 0 verified; 1 something differs, each difference listed; 2 it could not be checked (a file missing, a wrong command line, no browser).
